# LLM Wiki: Comprehensive Architecture, Operational Logic, Design Decisions, and Problem Resolutions

---

## 1. Executive Summary & Core Philosophy

### 1.1 The Andrej Karpathy Thesis
Traditional Retrieval-Augmented Generation (RAG) operates on a "query-time synthesis" paradigm: raw unstructured documents are split into static vector chunks, stored in a database, and dynamically retrieved whenever a user poses a question. While functional for simple lookups, standard RAG suffers from severe limitations as knowledge bases scale:
1. **Context Fragmentation:** Documents are arbitrarily cut across semantic boundaries, separating related facts and definitions across distinct chunks.
2. **Redundant Inference Costs:** Every question forces the language model to re-read, re-interpret, and re-synthesize raw text from scratch.
3. **Knowledge Inconsistency:** Because the LLM synthesizes an answer on the fly without a persistent source of truth, it frequently hallucinates conflicting answers to related queries.
4. **Lack of Human Inspectability:** The knowledge base exists purely as opaque high-dimensional floating-point vectors inside a database rather than a browsable, editable body of work.

**LLM Wiki** shifts this paradigm from query-time synthesis to **compile-time synthesis**, inspired by Andrej Karpathy’s formulation:
> *"Obsidian is the IDE; the LLM is the programmer; the wiki is the codebase."*

Instead of querying raw documents repeatedly, an LLM acts as an automated compiler and maintainer. When a raw document (research paper, book chapter, meeting transcript, or technical specification) enters the system, the LLM reads the document, extracts atomic concepts and entities, and compiles them into a structured, deeply interlinked network of plain Markdown notes. When knowledge changes, the LLM updates the existing notes, reconciles contradictions, and adjusts cross-references. At query time, answers are drawn directly from the pre-compiled, highly distilled wiki rather than thousands of raw pages.

### 1.2 Core Pillars of the System
- **Immutable Source Provenance:** Raw incoming documents are permanently preserved in an immutable directory (`raw/`) and are never modified or deleted by the compiler.
- **Compiled Human-Readable Vault:** All synthesized knowledge resides in standard GitHub-Flavored Markdown files inside an Obsidian vault (`wiki/`), organized into strict categories (`sources/`, `concepts/`, `entities/`, `topics/`, `comparisons/`, and `queries/`).
- **Strict Evidence Anchoring:** Every factual assertion in a compiled page must terminate in an explicit section citation back to the raw source (e.g., `[source: raw/paper.pdf, §3.2]`).
- **Human-in-the-Loop (HITL) Verification:** By default, the LLM cannot mutate the user’s vault silently. Proposed modifications are presented as unified visual terminal diffs requiring human approval.
- **Continuous Integrity Auditing:** Structural graph analyzers and Retrieval-Augmented Validation engines scan the vault for broken links, orphan pages, stale knowledge, and logical contradictions.
- **Centralized MCP Connectivity:** An always-on Model Context Protocol (MCP) router allows remote agentic clients (such as Antigravity, Hermes, or Claude Desktop) across a secure Tailscale network to navigate, query, and safely contribute to multiple independent wikis without needing local LLMs or vector database software.

## 2. System Architecture & Vault Topology

The project is strictly separated into two architectural layers:
1. **The LLM Wiki Engine Toolkit:** The Python engine, CLI utilities, provider abstractions, prompt templates, and background daemons located in the main codebase.
2. **Independent Wiki Vaults:** Isolated Obsidian vault directories (e.g., `~/wikis/ai-chats-wiki`, `~/wikis/vehicles-wiki`, `~/wikis/library-wiki`).

### 2.1 Directory Layout of an LLM Wiki Vault
Every wiki vault generated by `wiki init` maintains the following canonical directory structure:

- **`wiki.yaml`**: The instance configuration file. Defines the vault’s human-readable domain name, description, category taxonomy, required YAML frontmatter fields, confidence thresholds, and ingest/lint parameters.
- **`AGENTS.md`**: The editorial constitution. Serves as system prompt guidance and constraints for any autonomous LLM agent reading or writing to the vault.
- **`README.md`**: Human-facing vault overview and operational quick-start guide.
- **`page-templates/`**: Markdown template definitions for each note category (`concept.md`, `entity.md`, `topic.md`, `comparison.md`, `source.md`).
- **`raw/`**: The immutable archive for raw source documents.
  - **`assets/`**: Images, charts, and diagrams referenced by source documents.
  - **`inbox/`**: The safe landing drop-zone for notes deposited by remote MCP agents.
- **`wiki/`**: The compiled knowledge base managed by the LLM.
  - **`.llm-wiki/`**: Hidden internal state directory:
    - **`chroma_db/`**: Embedded persistent ChromaDB vector store files.
    - **`raw_cache/`**: Cached copies of previously ingested raw sources used for diff-based incremental re-ingestion.
    - **`hash_registry.json`**: Cryptographic MD5 hash and modification timestamp registry for skipping unchanged pages during linting.
    - **`.lint_state.json`**: Resumable audit checkpoint tracker.
  - **`index.md`**: The master table of contents and vault dashboard, regenerated automatically on every modification.
  - **`overview.md`**: High-level narrative summary of the domain knowledge.
  - **`log.md`**: Append-only timestamped audit log recording every ingestion, query, and lint fix.
  - **`sources/`**: Executive summaries and key takeaways of ingested raw documents.
  - **`concepts/`**: Theoretical principles, algorithms, and technical concepts (e.g., `regenerative-braking.md`, `lora.md`).
  - **`entities/`**: Concrete objects, organizations, hardware, models, or people (e.g., `tesla-model-3.md`, `roberta.md`).
  - **`topics/`**: Broad subject matter overviews clustering multiple concepts and entities.
  - **`comparisons/`**: Side-by-side comparative analyses between competing entities or paradigms.
  - **`queries/`**: High-value answers generated during user queries that were filed back into the vault for permanent retention.
- **`.obsidian/`**: Configuration directory for Obsidian, containing vault settings and custom CSS styling rules (`snippets/llm-wiki.css`) to highlight confidence badges and citation links.
- **`.git/`**: An independent Git repository tracking the entire version history of the vault, complete with automated pre-commit and post-commit hooks.

## 3. Detailed File-by-File & Function-by-Function Reference

This section provides an exhaustive walkthrough of every module and function across the core library (`lib/`) and the command-line interface (`cli/`), explaining inputs, outputs, algorithms, and operational logic without source code snippets.

### 3.1 The Core Library (`lib/`)

#### 3.1.1 `lib/config.py` (Configuration Management)
This module loads, parses, and validates YAML configuration files for both provider credentials and individual wiki vaults.
- **`class ProvidersConfig`**:
  - Encapsulates the global provider settings loaded from `providers.yaml`.
  - Maintains three primary attributes: `providers` (mapping of provider names to credentials, base URLs, and model pools), `fallback_chain` (mapping of operational task names to ordered lists of model IDs), and `token_limits` (per-task context window caps).
  - **`get_fallback_models(operation)`**: Accepts an operational string (e.g., `ingest_synth`, `lint_audit`, `query_answer`, or `embeddings`). Returns the configured ordered list of models for that operation. If the specific operation is not mapped, it searches for general fallback operations before defaulting to standard enterprise foundation models.
  - **`get_token_limit(limit_name, default)`**: Retrieves integer token thresholds for context windows, falling back to a safe default.
- **`class WikiConfig`**:
  - Represents the vault-level configuration parsed from `wiki.yaml`.
  - Contains vault metadata (domain name, slug, description), recognized page types, required frontmatter attributes, confidence thresholds, chunking parameters (strategy, maximum token size, overlap), and lint settings (staleness thresholds, citation requirements, orphan tolerances).
- **`find_providers_config(start_path)`**:
  - Searches the filesystem for `providers.yaml` across a prioritized search hierarchy: first checking explicit candidate directories, then the current working directory, then the global user config at `~/.config/llm-wiki/providers.yaml`, and finally the toolkit repository’s default configuration folder. Returns the resolved file path or `None`.
- **`load_providers_config(config_path)`**:
  - Reads and parses `providers.yaml` using a YAML parser.
  - Employs strict error interception: if a syntax error or malformed structure is encountered, it halts process execution with an informative standard error message rather than silently continuing with corrupted settings. If no file exists, it returns a blank configuration.
- **`load_wiki_config(wiki_dir)`**:
  - Locates `wiki.yaml` in the specified vault directory.
  - Extracts domain definitions, schema constraints, and operational settings, instantiating a fully populated `WikiConfig` instance. Missing values are filled with default conventions.

#### 3.1.2 `lib/providers.py` (Multi-Provider LLM & Cooldown Engine)
This module acts as the unified abstraction layer over multiple LLM cloud backends (Anthropic, OpenAI, Google Gemini, Groq, Nous Research, Cloudflare Workers AI) and local Ollama instances via LiteLLM.
- **`class LLMProviderError`**: Custom exception raised when every model across an operation's fallback chain fails or exhausts quota.
- **`class RateLimitCooldownTracker`**:
  - A global, in-memory rate-limit and quota tracker shared across all operations and vaults.
  - **`is_cooling_down(model_id)`**: Checks whether a model is currently in a cooldown window. If the expiration timestamp has passed, it automatically evicts the model from the cooldown registry and returns `False`.
  - **`mark_cooling_down(model_id, cooldown_seconds)`**: Sets an expiration timestamp for a model. Distinguishes between short-term rate limits (HTTP 429 / resource exhausted, cooling for 60 seconds) and daily quota exhaustions (free tier allocation depleted, cooling for 3,600 seconds).
  - **`clear()`**: Flushes all active cooldowns.
  - **`get_cooldowns()`**: Returns a snapshot dictionary of currently restricted models and their remaining cooldown durations in seconds.
  - **`filter_available_models(models)`**: Filters an input list of candidate models, stripping out any model currently cooling down. If *all* candidate models are cooling down, it bypasses the restriction and returns the original list to prevent systemic deadlocks.
- **`class LLMProvider`**:
  - The primary engine for executing text completions and vector embeddings.
  - **`_setup_environment()`**: Inspects loaded provider credentials and injects valid API keys and base URLs into the process environment variables, safely ignoring dummy placeholder strings.
  - **`_find_provider_for_model(model_id)`**: Inspects a model identifier string and matches it against configured providers based on explicit prefix mapping or model family heuristics (e.g., routing `gemini` to Google, `claude` to Anthropic, `ollama` or `qwen` to local endpoints).
  - **`call(messages, operation, temperature, override_model)`**:
    - Executes synchronous LLM completions with automated fallback failover.
    - Implements round-robin circular load balancing across available models using an internal call counter offset.
    - Sanitizes model strings for LiteLLM compatibility (stripping redundant prefixes, mapping Nous models to OpenAI-compatible paths, adjusting Cloudflare endpoints from `/ai/run` to `/ai/v1`).
    - Applies dynamic timeout scaling: standard operations receive 45 seconds, Cloudflare receives 60 seconds, and long-context synthesis or Nous Research tasks receive 180 seconds.
    - Executes calls with retry logic (attempting twice per model before failing over to the next candidate in the chain).
    - Inspects completion messages, properly handling modern reasoning models that return content in reasoning attributes.
    - Intercepts rate limits, logging errors and registering models with the cooldown tracker.
  - **`embed(text)`**:
    - Generates vector embeddings for a given text snippet using the model chain configured under the `embeddings` operation.
    - Iterates through candidate embedding models, injecting credentials, executing the vector computation, and returning a list of floating-point numbers.
  - **`acall(messages, operation, temperature, override_model)`**:
    - The asynchronous variant of `call`. Uses non-blocking asynchronous LiteLLM completions to permit concurrent chunk extraction, semantic page linting, and background streaming without thread starvation.
  - **`stream_call(messages, operation, temperature)`**:
    - A generator that streams completion tokens back to the caller in real-time as chunks arrive from the provider, enabling interactive terminal typing animations and streaming query responses.

#### 3.1.3 `lib/splitter.py` (Document Chunking & Context Pruning)
This module divides large raw documents into bounded text chunks optimized for LLM context windows while preserving structural coherence.
- **`class Chunk`**:
  - Data container holding chunked text content, chunk index, total chunk count, list of hierarchical headers leading to the section, and estimated token count.
- **`_prune_content(text)`**:
  - A pre-LLM context pruning step. Strips extraneous HTML tags while preserving page break annotations, simplifies verbose tracking URLs into concise tokens, and strips massive redundant markdown tables of contents to conserve token budgets before chunking.
- **`_split_by_headers(text, max_tokens)`**:
  - Hierarchical markdown splitter.
  - **First Pass:** Scans text line-by-line using regular expressions to detect header levels (`#` through `######`). Builds a running breadcrumb hierarchy of headings and accumulates text blocks.
  - **Second Pass:** Evaluates section sizes. If a section fits within the token cap, it is bundled with adjacent small sections to prevent over-fragmentation. If a section exceeds the token cap, it recursively subdivides it using horizontal rules, page break markers, or paragraph splits. If an individual block remains oversized, it applies a sliding window with overlap.
- **`_split_fixed_size(text, max_tokens, overlap_tokens)`**:
  - Sliding-window tokenizer. Converts text into words and moves a window forward using a fixed stride calculated from maximum tokens minus overlap. Dynamically trims slices that exceed token approximations.
- **`_split_by_pages(text)`**:
  - Splits text using explicit page-break demarcations such as form feed characters, HTML page break comments, or horizontal separator rules. Annotates each chunk with a virtual page index.
- **`_cosine_similarity(vec1, vec2)`**:
  - Computes the geometric cosine similarity between two vector embeddings by calculating their dot product divided by the product of their Euclidean norms.
- **`_split_semantic(text, provider, max_tokens)`**:
  - Semantic boundary detector. Splits text into paragraphs, computes vector embeddings for each paragraph via the provider, and evaluates cosine similarity between consecutive paragraphs. Calculates the mean similarity and standard deviation across the document. Paragraph transitions where similarity falls below a statistical threshold (mean minus half standard deviation) are flagged as topic shifts and chosen as chunk boundaries, preventing semantic fragmentation.
- **`split_document(text, strategy, max_tokens, overlap_tokens, provider)`**:
  - Master chunking dispatcher. Prunes raw boilerplate, evaluates whether the document already fits within the token limit (returning a single chunk if so), and delegates to the requested strategy (`headers`, `fixed_size`, `pages`, or `semantic`).

#### 3.1.4 `lib/diff_tracker.py` (Incremental Delta Computation)
This module enables efficient re-ingestion of modified documents by isolating altered text blocks rather than re-compiling entire multi-megabyte files.
- **`get_diff_deltas(old_text, new_text, context_lines)`**:
  - Uses Python’s `difflib.SequenceMatcher` to compare lines of previously cached raw text against newly modified raw text.
  - Evaluates matching opcodes across three alteration types: `insert`, `replace`, and `delete`.
  - For each changed section, it expands the boundary to capture surrounding context lines and scans backward to identify the nearest preceding markdown heading.
  - Formats the delta into a clearly demarcated block detailing deleted passages, inserted passages, and structural context. Multiple disparate change blocks are joined with separator ellipsis markers.
  - This guarantees that deletions are explicitly surfaced to the LLM compiler so obsolete assertions can be pruned from the wiki.

#### 3.1.5 `lib/differ.py` (Human-in-the-Loop Review Engine)
This module safeguards the user’s Obsidian vault by ensuring that all LLM-synthesized mutations undergo visual inspection and manual approval.
- **`class FileChange`**:
  - Represents a proposed vault mutation: target relative file path, operation type (`create`, `update`, or `delete`), new content, old content (if updating or deleting), and the LLM’s underlying rationale.
- **`_render_unified_diff(old_text, new_text, file_path)`**:
  - Generates standard unified diff representations comparing existing file text against proposed replacements, complete with file labels and line markers.
- **`print_change_summary(changes, console)`**:
  - Renders a clean terminal table summarizing all proposed actions, highlighting operations in distinct colors (green for creations, yellow for modifications, red for deletions) alongside paths and rationale notes.
- **`review_changes(changes, auto_approve, console)`**:
  - Interactive review controller.
  - If `auto_approve` is active (e.g., in automated watcher mode or non-interactive CI/CD runs), it immediately returns all proposed changes.
  - In interactive mode, it displays the change summary table and prompts the user with three options: `[a]` approve all changes, `[r]` review changes step-by-step, or `[s]` reject all changes.
  - In step-by-step mode, it iterates through each modification individually, displaying full content panels for new notes, unified syntax-highlighted diffs for updates, and deletion warnings, prompting the reviewer for an individual yes/no decision on each file.
  - Includes an environment safety guard: if standard input is not attached to an interactive terminal and auto-approval is not enabled, it aborts execution to prevent unintended automated vault modifications.

#### 3.1.6 `lib/vector_store.py` (ChromaDB Vector Management)
This module manages an embedded ChromaDB vector store hidden within the vault's `.llm-wiki` folder, providing fast semantic retrieval for linting and querying.
- **`class WikiVectorStore`**:
  - **`__init__(wiki_dir, provider)`**: Resolves the internal database path at `<vault>/wiki/.llm-wiki/chroma_db`, initializes a persistent Chroma client with telemetry disabled, and creates or retrieves the `wiki_pages` collection configured with cosine distance space.
  - **`embed_and_upsert(page_id, text, metadata)`**: Generates a vector embedding for a page using the provider and executes an upsert operation into ChromaDB, updating the embedding, raw document text, and metadata dictionary under the unique relative file path.
  - **`search_similar(text, k, distance_threshold)`**: Generates an embedding for the query text, searches the collection for the `k` nearest neighbors, extracts distances, and filters the returned documents against the maximum allowable distance threshold (guaranteeing at least two context documents are returned if available). Returns a list of raw markdown content strings.
  - **`search_similar_with_metadata(text, k, distance_threshold)`**: The metadata-rich variant of similarity search. Returns a structured list of dictionaries containing the file path, page title, document body, and rounded cosine distance for each matching node.

#### 3.1.7 `lib/utils.py` (Markdown Parsing, Graph Analysis, & Vault Resolution)
This module houses essential utility functions supporting text parsing, frontmatter manipulation, link graph computation, and filesystem resolution.
- **`today_str()`**: Returns the current ISO date string (`YYYY-MM-DD`).
- **`slugify(title)`**: Strips non-alphanumeric characters, converts strings to lowercase, collapses consecutive spaces and dashes, and produces clean kebab-case slugs suitable for filenames and wiki links.
- **`parse_frontmatter(content)`**: Uses regular expressions to extract the opening YAML frontmatter block from markdown documents, parses it via PyYAML, and returns a tuple of the metadata dictionary and the markdown body text.
- **`render_frontmatter(frontmatter, body)`**: Serializes a Python dictionary into clean YAML with consistent indentation and prepends it to markdown body text enclosed in triple-dash fences.
- **`extract_wikilinks(content)`**: Scans markdown text using regular expressions to identify all `[[target]]` and `[[target|label]]` internal links, returning a list of target note names.
- **`extract_source_citations(content)`**: Scans markdown text for inline citations conforming to the `[source: filename.md, §section]` format, extracting source references.
- **`count_tokens_approx(text)`**: Approximates token counts using `tiktoken` (cl100k_base encoding) if available, falling back to a character heuristic (approximately 4 characters per token in English).
- **`build_link_graph(wiki_dir)`**: Recursively scans all markdown notes in a directory (ignoring internal `.llm-wiki` cache files), extracts all outbound wikilinks, and constructs a bidirectional adjacency graph mapping file stems to sets of linked targets.
- **`read_source_file(file_path)`**: Reads raw source documents. For standard text and markdown files, it reads UTF-8 content directly. For PDF documents, it invokes `pymupdf4llm` to convert the binary pages into structured markdown text before processing.
- **`list_available_vaults()`**: Scans common filesystem locations (current working directory, `./wikis/`, and `~/wikis/`) for folders containing a valid `wiki/` directory, returning a deduplicated list of discovered vault paths.
- **`resolve_vault_path(wiki_arg, query)`**:
  - Implements smart vault resolution.
  - If an explicit path or name is supplied: checks direct filesystem paths, then scans `~/wikis` and `./wikis` for exact matches, `-wiki` suffixes, or clean prefix matches.
  - If omitted or defaulted to current directory: checks if the current directory is a vault; if not, checks standard locations. If exactly one vault exists, it is selected automatically. If multiple vaults exist and a query string is provided, it matches the query against vault names and internal note titles to automatically infer the target vault.

#### 3.1.8 `lib/wiki_ops.py` (Master Orchestrator)
The central operational pipeline of LLM Wiki, orchestrating ingestion, querying, linting, index updates, and automated Map of Content generation.
- **`class SynthesisParseError`**: Exception raised when LLM synthesis completions cannot be parsed into valid structural modifications.
- **`get_template(name)`**: Loads a Jinja2 prompt template from the `prompts/` directory with automatic whitespace trimming.
- **`_clean_json_response(raw_text)`**: Strips markdown code fences (` ```json `), extracts substrings bounded by square brackets or curly braces, and prepares raw LLM text for JSON deserialization.
- **`parse_json_relaxed(text)`**: A four-tier JSON recovery parser. Attempts standard `json.loads`, then non-strict parsing, then `json_repair`, and finally `jiter` in trailing-string mode, guaranteeing that minor formatting deviations from the LLM do not cause pipeline crashes.
- **`_validate_and_resolve_path(wiki_dir, rel_path)`**: A critical path validation check. Resolves the full path of a proposed modification and asserts that it remains strictly inside the `<vault>/wiki/` directory, preventing directory traversal attacks.
- **`update_wiki_index(wiki_dir, new_pages)`**: Scans all subdirectories of `wiki/`, tallies note counts across categories, extracts titles and source counts from frontmatter, and rewrites `wiki/index.md` with an updated master table of contents and summary statistics. Automatically triggers dynamic MOC regeneration.
- **`generate_mocs(wiki_dir)`**: Computes inbound backlink counts across the vault, iterates through category folders (`concepts`, `entities`, `topics`), extracts first-paragraph summaries and confidence tags, sorts notes by inbound link popularity, and writes dynamic Map of Content dashboards (e.g., `Concepts_MOC.md`).
- **`append_to_log(wiki_dir, operation, title, details)`**: Appends a structured, timestamped log entry to `wiki/log.md`.
- **`commit_if_git(wiki_dir, message)`**: Detects if the vault is a Git repository, stages all changes, and records a commit with the specified message.
- **`vector_cross_reference_pages(wiki_dir, synth_files, store, distance_threshold, max_links_per_new_page)`**:
  - Zero-token vector cross-referencing engine.
  - Takes newly synthesized pages, searches ChromaDB for semantically related existing notes, verifies that targets are not already linked, and injects markdown links (`[[New Note]]`) into existing files under their `## Related` or `## See Also` sections using regex manipulation, completely eliminating an LLM pass.
- **`run_ingest(source_file, wiki_dir, provider, auto_approve)`**:
  - The master ingestion controller.
  - Reads the source file (converting PDFs if necessary) and checks the raw cache. If the file was previously ingested, it calculates diff deltas; if unchanged, it exits early.
  - Splits content into chunks and launches concurrent extraction tasks via `ingest_extract.md` throttled by an asyncio semaphore and pacing delays.
  - If more than four chunks exist, it executes a two-tier aggregation pass, compacting extraction results into a dense payload (summaries, prominent entities, concepts, claims, relationships) bounded under 3,500 tokens.
  - Invokes `ingest_synthesize.md` to generate complete markdown pages.
  - Validates proposed pages against minimum length (>100 characters), frontmatter completeness, and existing title collisions.
  - Executes the numeric claim verification check: extracts all numbers in the synthesized body, verifies their existence in the raw source, and downgrades unverified claims to `confidence: low` rather than discarding the page.
  - Executes cross-referencing (preferring vector automation, falling back to `ingest_crossref.md`).
  - Presents proposed changes to the user via `review_changes`, writes approved files to disk, regenerates `index.md`, appends to `log.md`, records a Git commit, and saves the source to the raw cache.
- **`run_query(question, wiki_dir, provider, file_back, use_hybrid, store)`**:
  - Question answering engine.
  - Performs entity matching between query terms and vault note titles. If a core entity is matched, it applies graph-based query truncation, loading the matched note and its 1st-degree topological neighbors while excluding unrelated notes.
  - If hybrid search is requested, invokes external `qmd` subprocesses. Otherwise, executes vector similarity search in ChromaDB.
  - Renders `query_answer.md` with retrieved context and synthesizes a grounded answer with inline citations.
  - If `file_back` is active, invokes `query_fileback.md` to format the answer into a permanent markdown note saved to `wiki/queries/<slug>.md`, updating the index, logging the action, and committing to Git.
- **`run_lint(wiki_dir, provider, fix, auto_approve, reset, max_pages, staged_only)`**:
  - The comprehensive health check engine.
  - In `staged_only` mode, inspects staged Git files to perform micro-linting.
  - Performs structural checks: detects broken wikilinks, dangling raw source citations, missing frontmatter attributes, and orphan pages with zero inbound links.
  - Performs zero-token mechanical checks: scans concepts, entities, and topics for missing inline citations and flags pages exceeding staleness thresholds (e.g., unmodified for over 30 days).
  - If an LLM provider is present: hashes page bodies against `hash_registry.json`, skipping unchanged files. Upserts modified pages into ChromaDB.
  - Prioritizes the audit queue using confidence weighting (`contested` and `low` confidence notes are audited first).
  - Concurrently audits pages via `lint_audit.md` using topological neighbors and vector context, recording progress in `.lint_state.json` to allow resumption if interrupted.
  - If `fix` mode is enabled, passes identified issues to `lint_fix.md`, generating patch proposals reviewed via `differ.py`.
- **`emit_progress(message, progress)`**: Transmits background progress notifications via HTTP POST to the local dashboard web server if active.

#### 3.1.9 `lib/mcp_router.py` (Centralized Multi-Wiki Gateway)
This module powers the centralized Server-Sent Events gateway that exposes all wiki vaults on the host machine to remote AI agents over the network.
- **`resolve_page_path(wiki_dir, page_slug)`**: Resolves incoming page slugs to real filesystem paths using direct relative paths, extension appending (`.md`), and case-insensitive stem scanning, while enforcing strict vault boundary containment.
- **`class WikiRouterManager`**:
  - Central manager maintaining discovery and caching across all vaults in `base_dir`.
  - Maintains `_store_cache` (caching active `WikiVectorStore` ChromaDB clients in memory) and `_config_cache` (caching parsed `WikiConfig` instances).
  - **`resolve_wiki(wiki_name)`**: Validates vault directory names, blocking path traversal characters and verifying that `<vault>/wiki` exists.
  - **`get_wiki_config(wiki_name)`**: Retrieves or lazily loads the vault’s configuration.
  - **`get_vector_store(wiki_name)`**: Retrieves or lazily initializes the persistent ChromaDB client for a vault.
  - **`list_wikis()`**: Dynamically scans `base_dir`, returning name, description, and total page count for all discovered vaults.
  - **`get_wiki_skeleton(wiki_name, category)`**: Generates a complete hierarchical table of contents of note slugs grouped by category.
  - **`get_wiki_status(wiki_name)`**: Computes high-level structural metrics (total pages, raw sources, category counts).
  - **`read_wiki_page(wiki_name, page_slug)`**: Retrieves the raw markdown content of a specified note.
  - **`get_page_links(wiki_name, page_slug)`**: Computes outgoing wikilinks and incoming backlinks for a given note.
  - **`get_entity_info(wiki_name, entity_name)`**: Returns rich frontmatter metadata, source lists, links, and the first-paragraph summary for an entity.
  - **`query_wiki(wiki_name, query)`**: Executes a semantic RAG query against a vault using the server’s vector store and provider fallback chain.
  - **`add_inbox_note(wiki_name, title, content, tags)`**: Writes a new note into `raw/inbox/<date>-<slug>.md` with frontmatter, enabling remote agents to contribute research safely without causing file sync merge conflicts.
  - **`append_to_log(wiki_name, entry_text)`**: Records a timestamped research finding directly into `wiki/log.md`.
  - **`search_wiki(wiki_name, query, limit)`**: Executes lightweight semantic vector search returning snippets and similarity distances with zero LLM synthesis tokens.
  - **`search_all_wikis(query, limit_per_wiki)`**: Executes federated semantic search across all registered vaults on the server.
  - **`get_recent_changes(wiki_name, days, limit)`**: Returns a chronological list of recently created or modified notes across one or all vaults.
  - **`get_graph_insights(wiki_name)`**: Analyzes graph structure, reporting link density, top authority hub pages, orphan notes, and dead links.
  - **`get_router_health()`**: Reports service health, discovered vaults, cached vector stores, and active provider rate-limit cooldowns.

### 3.2 The Command-Line Interface (`cli/`)

#### 3.2.1 `cli/main.py`
The CLI entry point powered by `click`.
- Configures global logging and registers all subcommands (`init`, `ingest`, `query`, `lint`, `status`, `setup`, `watch`, `export`, `mcp`, `mcp-router`, `dashboard`, `moc`, `install-hooks`).
- **`status_cmd(wiki_path)`**: Resolves the target vault, counts files across categories, formats a status table with Rich, displays total compiled pages, and checks Git commit metadata.

Scaffolds a new Obsidian vault from repository templates.
- **`render_template_file(file_path, variables)`**: Replaces template variable markers (`{{KEY}}`) in scaffolding files.

Interactive terminal wizard for configuring LLM providers and credentials.

Dispatcher for ingesting raw source documents.

#### 3.2.5 `cli/query_cmd.py`
Dispatcher for question answering against the wiki.
- **`query_cmd(question, wiki_path, file_back, hybrid, stream)`**: Automatically resolves the target vault based on question context. In streaming mode, initializes the vector store, constructs the query prompt, and streams answer tokens directly to the terminal. In standard mode, executes `run_query` and displays markdown answers within Rich panels.

#### 3.2.6 `cli/lint_cmd.py`
Dispatcher for structural and semantic health checks.
- **`discover_wikis(base_dir, wiki_path)`**: Discovers vaults across individual paths or base directories.
- **`audit_single_wiki(wiki_dir, provider, fix, yes, reset, max_pages, staged)`**: Executes `run_lint`, formats broken links, orphan notes, mechanical issues, and semantic contradictions into summary tables, and applies automated repairs if requested.
- **`lint_cmd(...)`**: Batch controller running audits across discovered vaults.

#### 3.2.7 `cli/watch_cmd.py`
Autonomous 24/7 background file watcher daemon.
- **`get_raw_files_state(raw_dir)`**: Returns a snapshot mapping relative files in `raw/` to modification times and file sizes.
- **`get_already_ingested(wiki_dir)`**: Inspects `wiki/sources/` and `wiki/log.md` to identify already compiled files.
- **`watch_cmd(base_dir, wiki_path, interval, yes, lint, lint_fix, lint_interval)`**:
  - Enters a continuous polling loop monitoring `raw/` across all watched vaults.
  - Dynamically discovers newly added vaults dropped into the base directory.
  - Implements a 15-iteration size and modification time stability debounce loop to ensure that editor saves or network file transfers (such as Syncthing) have completely finished writing before ingestion begins.
  - Automatically compiles detected documents via `run_ingest`.
  - Triggers automated post-ingest linting and periodic scheduled audits across vaults.

#### 3.2.8 `cli/mcp_router_cmd.py`
Launcher for the centralized Multi-Wiki MCP Router.
- **`create_mcp_router_server(base_dir, provider)`**: Instantiates `MCPServer`, connects `WikiRouterManager`, and decorates all 14 discovery, querying, reading, traversal, insight, telemetry, and contribution tools.
- **`mcp_router_cmd(base_dir, host, port, log_level)`**: Boots the Starlette/Uvicorn ASGI server over Server-Sent Events bound to the designated network interface.

#### 3.2.9 `cli/mcp_cmd.py`
Legacy single-vault MCP server exposing an individual wiki vault over standard input/output (stdio) for local tools like Claude Desktop.

#### 3.2.10 `cli/hooks_cmd.py`
Installs automated Git CI/CD hooks into vault repositories.
- **`install_hooks_cmd(wiki_path, force)`**: Writes an executable `.git/hooks/pre-commit` script (running `wiki lint --staged --yes` to micro-lint only staged notes before commits) and a `.git/hooks/post-commit` script (silently refreshing Maps of Content and index files).

#### 3.2.11 `cli/moc_cmd.py`
CLI dispatcher invoking `generate_mocs(wiki_dir)` to rebuild Map of Content dashboards on demand.

#### 3.2.12 `cli/export_cmd.py`
Flattens the entire compiled wiki into a single, LLM-optimized `llm.txt` context file, stripping frontmatter boilerplate and converting wikilinks to plain text for ingestion by external AI models.

FastAPI web server providing a browser-based dashboard with a live Server-Sent Events progress bar and message log stream.

## 4. The Multi-Stage LLM Prompt & Processing Pipeline

The compilation process is broken into discrete, specialized prompt stages stored in `prompts/`.

```
Raw Document (.md, .txt, .pdf)
       │
       ▼
 [Context Pruning & Chunking] (splitter.py)
       │
       ▼
 ┌────────────────────────────────────────────────────────┐
 │ Stage 1: Extraction (ingest_extract.md)                │
 │ Extracts entities, concepts, claims, caveats into JSON │
 └────────────────────────────────────────────────────────┘
       │
       ▼
 [High-Chunk Aggregation & Deduplication] (<3,500 tokens)
       │
       ▼
 ┌────────────────────────────────────────────────────────┐
 │ Stage 2: Synthesis (ingest_synthesize.md)              │
 │ Compiles complete markdown pages with YAML frontmatter │
 └────────────────────────────────────────────────────────┘
       │
       ▼
 [Validation Gates: Completeness, Titles, Numeric Check]
       │
       ▼
 ┌────────────────────────────────────────────────────────┐
 │ Stage 3: Cross-Referencing                             │
 │ Vector-Automated (Zero-Tokens) OR ingest_crossref.md   │
 └────────────────────────────────────────────────────────┘
       │
       ▼
 [Human-in-the-Loop Review / Diff Engine] (differ.py)
       │
       ▼
 [Disk Persistence, Index Update, MOC Sync, Git Commit]
```

### 4.1 Stage 1: Extraction (`prompts/ingest_extract.md`)
- **Objective:** Read an individual document chunk and extract atomic factual data into a rigid JSON structure.
- **Injected Context:** Domain name, source filename, chunk index/total, header breadcrumb path, and raw chunk text.
- **Rules:** The LLM is prohibited from writing conversational prose. It must output a JSON object containing an executive summary, a list of entities (with names, types, and bulleted facts), concepts (with definitions and properties), core factual claims (each requiring an explicit section citation anchor like `§3.1`), entity relationships, and contradictions or caveats.

### 4.2 Intermediate Stage: High-Chunk Payload Aggregation
- **Objective:** Prevent context window overflow during synthesis when ingesting massive multi-chunk documents (e.g., 50+ page PDFs).
- **Logic:** If an ingestion run produces more than four chunks, the engine aggregates extractions before calling the synthesizer. It groups summaries chronologically, maps entities and concepts into frequency dictionaries, tallies occurrences, preserves top facts, and filters the top 14 entities and 10 concepts. This compresses massive documents into a dense payload guaranteed to remain under 3,500 tokens.

### 4.3 Stage 2: Synthesis (`prompts/ingest_synthesize.md`)
- **Objective:** Transform aggregated extractions into production-grade Obsidian markdown notes.
- **Injected Context:** Domain name, source metadata, compacted extractions, current `wiki/index.md` content, markdown page templates, and maximum page word count constraints.
- **Rules:**
  1. Compiles a primary source summary note at `wiki/sources/<slug>.md`.
  2. Selects the top 6 to 8 most prominent entities and concepts.
  3. Enforces note deduplication: if an entity already exists in `index.md`, it *must* update the existing file rather than creating a parallel duplicate.
  4. Filenames must strictly use lowercase kebab-case.
  5. Outputs a strict JSON array of file operation objects (`path`, `operation`, `content`, `reason`).

### 4.4 Stage 3: Cross-Referencing
- **Vector-Automated (Zero-Token Default):** When a new note is synthesized, the engine queries ChromaDB for the most semantically related existing notes in the vault. If related notes are found and do not yet link to the new note, the engine automatically injects `[[New Note]]` links into their `## Related` sections using Python regex. This eliminates an entire LLM call, saving approximately 33% of total ingestion tokens.
- **LLM Fallback (`prompts/ingest_crossref.md`):** If vector search is unavailable, candidate existing notes are fed to the LLM alongside the new extractions to identify contextual cross-references.

### 4.5 Query Pipelines
- **Answer Generation (`prompts/query_answer.md`):** Receives the user question alongside retrieved context notes (derived from graph truncation or vector search). Synthesizes an authoritative answer, incorporating internal `[[wikilinks]]` and inline source citations.
- **Query Filing (`prompts/query_fileback.md`):** Transforms high-value answers into standalone markdown notes formatted with full frontmatter, filing them permanently into `wiki/queries/<slug>.md`.

### 4.6 Audit & Repair Pipelines
- **Semantic Audit (`prompts/lint_audit.md`):** Receives a target note along with its 1st-degree topological neighbors and semantically similar context notes retrieved from ChromaDB. Audits the notes for logical contradictions, missing citations, or factual drift, outputting structured issue reports.
- **Automated Fix (`prompts/lint_fix.md`):** Receives structural and semantic issues from the audit report, proposing JSON patches to repair broken links, insert citations, or reconcile contradictions.

## 5. Retrieval, Verification, and Trust Stack

To ensure that autonomous LLM operations do not degrade the accuracy of the vault over time, LLM Wiki implements a rigorous trust stack:

### 5.1 Graph-Based Query Truncation
Standard RAG retrieves notes based purely on text similarity, often pulling irrelevant documents that share coincidental keywords. LLM Wiki implements topological graph truncation:
1. When a query targets an entity, the engine detects the entity note stem.
2. It builds the vault’s adjacency graph and selects the entity along with its 1st-degree inbound and outbound neighbors.
3. Only this tightly interconnected cluster is loaded as context, pruning unrelated branches of the vault and drastically improving precision while minimizing prompt tokens.

### 5.2 Numeric Claim Verification Gate
LLMs frequently hallucinate precise numerical specifications (e.g., battery capacities, dates, torque figures). During ingestion synthesis:
1. A regex scanner extracts all numeric tokens from the synthesized note body.
2. Every number is checked against the raw source text and existing index.
3. If an unverified number is detected, the engine does not discard the note (which would cause information loss); instead, it rewrites the YAML frontmatter, downgrading `confidence: high/medium` to `confidence: low`.

### 5.3 Retrieval-Augmented Semantic Validation
During vault linting, pages are not audited in isolation. For every page being audited:
1. The engine pulls its explicit topological graph neighbors.
2. It queries ChromaDB to find dynamically similar notes across disparate folders.
3. Both sets are presented to the auditor model simultaneously, allowing the model to detect subtle cross-page contradictions.

### 5.4 Confidence-Weighted Lint Scheduling
To conserve API costs on large vaults, lint queues are prioritized based on the `confidence:` attribute in YAML frontmatter. Notes marked `contested` or `low` confidence are placed at the front of the audit queue, while `high` confidence notes are audited infrequently.

## 7. Background Automation & Daemon Services

LLM Wiki is designed to operate autonomously in the background via Linux systemd user services.

### 7.1 Automated Ingestion & Linting Watcher
- **Service Unit:** `~/.config/systemd/user/llm-wiki-watcher.service`
- **Command:** `wiki watch --base-dir /home/ubuntu/wikis --yes --lint --lint-interval 21600`
- **Operation:** Polls `raw/` across all vaults every 2 seconds. When a new file is dropped, it waits for file size and timestamp stability, compiles the document into the wiki, and runs post-ingest linting. Runs a scheduled vault-wide audit every 6 hours.

### 7.2 Multi-Wiki MCP Router Service
- **Service Unit:** `~/.config/systemd/user/llm-wiki-router.service`
- **Command:** `wiki mcp-router --base-dir /home/ubuntu/wikis --host 100.99.243.66 --port 8765`
- **Operation:** Maintains the persistent Starlette SSE server, automatically restarting on failure.

### 7.3 Persistent Process Execution (Linger)
Both services run under the unprivileged `ubuntu` user account. Persistence across SSH disconnects and system reboots is guaranteed by enabling systemd user lingering:
```bash
loginctl enable-linger ubuntu
```

### 7.4 Git CI/CD Automation Hooks
Installed via `wiki install-hooks`:
- **`pre-commit`**: Executes `wiki lint --staged --yes` before any commit is finalized. If syntax errors, broken links, or frontmatter defects exist in staged notes, the commit is blocked.
- **`post-commit`**: Executes `wiki moc --wiki-path "$PWD"`, silently regenerating Map of Content dashboards and updating `index.md` whenever changes are committed.

## 8. Architectural & Design Choices: What Was Chosen & Why

### 8.1 Compiled Markdown vs. Database Storage
- **Choice:** Maintain the knowledge base as plain Markdown files in an Obsidian vault rather than storing knowledge in a relational or vector database.
- **Rationale:** Plain Markdown is human-inspectable, future-proof, portable across operating systems, and natively supported by tools like Obsidian. It allows users to read, edit, and link their knowledge without specialized software.

### 8.2 Decoupled Engine vs. Independent Vaults
- **Choice:** Maintain the compiler toolkit at `/home/ubuntu/llm wiki` while keeping individual vaults completely separate in `~/wikis/`.
- **Rationale:** Decoupling prevents tool dependencies and temporary build artifacts from polluting user notes. Each vault maintains its own Git repository, domain configuration, and commit history.

### 8.3 Three-Stage Pipeline vs. Monolithic Prompting
- **Choice:** Split document ingestion into Extract -> Synthesize -> Cross-reference instead of a single giant prompt.
- **Rationale:** Monolithic prompts that attempt to extract facts, design page structures, and cross-reference existing notes simultaneously suffer from attention decay, missed entities, and severe hallucinations. Specialized stages enforce rigorous separation of concerns.

### 8.4 Multi-Model Fallback Chains with Global Cooldowns
- **Choice:** Abstract model execution behind operational fallback chains backed by a shared cooldown tracker.
- **Rationale:** Cloud LLM providers frequently encounter rate limits (HTTP 429), capacity outages (HTTP 503), or quota exhaustion. A shared cooldown tracker allows the engine to immediately bypass exhausted models without waiting on repetitive failed network requests.

### 8.5 Safe Remote Contribution Paths
- **Choice:** Prohibit remote MCP agents from mutating compiled markdown notes directly; force contributions through `raw/inbox/` and `wiki/log.md`.
- **Rationale:** Remote agents editing compiled pages directly over the network while Syncthing is synchronizing the vault causes severe file conflict forks. Depositing atomic files into `raw/inbox/` allows the local watcher to ingest and integrate notes deterministically without concurrency collisions.

## 9. Chronology of Limitations, Problems Encountered, & Resolutions

Throughout the design, testing, and production deployment of LLM Wiki, numerous edge cases, security vulnerabilities, and operational bugs were identified and systematically resolved:

### 1. Silent Null Return in Vector Similarity Search (F-01)
- **Problem:** In `lib/vector_store.py`, `WikiVectorStore.search_similar` filtered nearest neighbors by distance threshold into an internal list but omitted a return statement at the end of the method, implicitly returning `None`. When called during semantic linting, list comprehensions iterating over `None` raised `TypeError`, crashing the entire audit pipeline.
- **Resolution:** Added the missing return statement returning valid documents and added comprehensive unit tests verifying non-null list returns.

### 2. Path Traversal Vulnerability via Relative Prefixes (F-02)
- **Problem:** `_validate_and_resolve_path` verified that candidate paths started with `wiki/` using a raw string prefix check before resolving relative dots. An adversarial or buggy LLM output specifying `wiki/concepts/../../wiki.yaml` passed the prefix check and resolved to `<vault>/wiki.yaml`, allowing the LLM to overwrite root configuration files, `AGENTS.md`, or `README.md`.
- **Resolution:** Updated the path validation logic to resolve the absolute path first and strictly verify that it remains a subdirectory of the resolved `<vault>/wiki` folder using path containment checks.

### 3. Deletion Omission in Incremental Diff Tracker (F-03)
- **Problem:** `lib/diff_tracker.py` evaluated `SequenceMatcher` opcodes but only processed `insert` and `replace` tags, completely ignoring `delete`. When text was removed from a source document, the extracted delta was empty, causing `run_ingest` to report no meaningful changes and skip re-ingestion, leaving stale facts in the wiki.
- **Resolution:** Added explicit handling for `delete` opcodes in `get_diff_deltas`, generating clear deletion blocks (`[- DELETED: ... -]`) with surrounding context so the synthesizer is informed of removed content.

### 4. Missing Embeddings Chain in Setup Wizard (F-04)
- **Problem:** `cli/setup_cmd.py` configured fallback chains for `ingest`, `query`, and `lint`, but omitted the `embeddings` key. Users configuring providers via the CLI wizard ended up with broken embedding chains, causing `embed()` to return `None` and leaving vector stores empty.
- **Resolution:** Updated `setup_cmd.py` and `providers.example.yaml` to include default embedding model chains (`local/ollama/nomic-embed-text`, `google/gemini/text-embedding-004`).

### 5. Chunk Token Overflow on Massive Documents
- **Problem:** When ingesting oversized source articles (such as 125KB Wikipedia articles or academic PDFs), large sections with sparse headers produced chunks exceeding 10,000 tokens, instantly breaching provider rate limits (such as Groq's 8,000 TPM limit).
- **Resolution:** Updated `lib/splitter.py` to enforce strict sliding-window sub-chunking whenever a header section exceeds `chunk_max_tokens`, splitting oversized blocks into sub-chunks of 2,000 tokens with 200-token overlap.

### 6. Synthesis Context Window Overflow on Multi-Chunk Documents
- **Problem:** Ingesting 10+ chunk documents produced massive extraction payloads that exceeded LLM context windows during the synthesis stage, causing API failures.
- **Resolution:** Implemented high-chunk payload aggregation in `lib/wiki_ops.py`. When an extraction produces more than four chunks, the engine extracts summaries, maps entities and concepts into frequency tables, strips low-frequency items, and condenses the payload to under 3,500 tokens before synthesis.

### 7. Overly Aggressive Discarding of Unverified Numeric Claims
- **Problem:** The numeric verification gate originally discarded entire synthesized pages if a single number could not be found in the raw source text. This caused massive data loss when the LLM made valid mathematical conversions (e.g., converting kilometers to miles) or formatted numbers with commas.
- **Resolution:** Sanitized number comparisons (stripping commas) and modified the gate: unverified numbers now trigger a frontmatter downgrade to `confidence: low` rather than discarding the entire page.

### 8. Empty Provider Completions & Reasoning Model Attribute Divergence
- **Problem:** Modern reasoning models (e.g., DeepSeek R1, Qwen 2.5 Max) frequently returned empty strings in the standard `message.content` attribute while placing output in `message.reasoning_content`. Furthermore, temporary provider hiccups occasionally returned blank content strings without throwing HTTP errors, leading to downstream JSON parsing crashes.
- **Resolution:** Updated `lib/providers.py` to inspect `reasoning_content` if `content` is blank, and explicitly raise retryable `LLMProviderError` exceptions when true empty content is received, prompting automatic failover to the next fallback model.

### 9. Provider Model Name Prefix Incompatibilities
- **Problem:** LiteLLM rejected model strings from Nous Research when passed without provider prefixes, and Cloudflare Workers AI rejected default base URLs formatted with `/ai/run`.
- **Resolution:** Added model string normalization in `lib/providers.py` to automatically prepend `openai/` to Nous Research models and rewrite Cloudflare base URLs to `/ai/v1`.

### 10. Rate Limit Cooldown Granularity (Daily vs. Per-Minute Limits)
- **Problem:** A uniform 60-second cooldown was applied to all rate limit errors. When a provider exhausted its daily quota allocation, the model was un-flagged after 60 seconds, immediately retried, and failed again, creating a continuous error cycle.
- **Resolution:** Enhanced `RateLimitCooldownTracker` to inspect error strings for quota exhaustion keywords (`daily`, `free allocation`, `exceeded your current quota`), assigning a 1-hour (3,600s) cooldown for daily exhaustion while retaining 60-second cooldowns for temporary per-minute rate limits.

### 11. Timeout Failures During Heavy Synthesis Operations
- **Problem:** Standard API call timeouts (30 seconds) caused complex multi-page synthesis prompts and slow open-source models (such as Nous Research) to abort mid-stream.
- **Resolution:** Scaled operation timeouts dynamically: complex synthesis (`ingest_synth`), repair operations (`lint_fix`), and Nous models are granted 180-second execution windows.

### 12. Lint False Positives on Internal Caches and Dashboards
- **Problem:** `wiki lint` recursively scanned all `.md` files in the vault, attempting to audit internal cache files in `.llm-wiki/raw_cache/` and generated dashboards (`index.md`, `overview.md`, `log.md`, `*_MOC.md`). This produced hundreds of false-positive warnings for missing frontmatter and broken links.
- **Resolution:** Excluded `.llm-wiki` directories and all administrative dashboard files from structural and semantic lint loops in `lib/wiki_ops.py` and `lib/utils.py`.

### 13. Broken Wikilink False Positives on YAML Title Aliases
- **Problem:** The link resolver originally matched `[[wikilinks]]` solely against file stems on disk. Notes linking to human-readable titles defined in frontmatter (e.g., `[[Liquid Electrolyte]]` pointing to `liquid-electrolyte-battery.md`) were incorrectly reported as broken.
- **Resolution:** Overhauled `build_link_graph` and `run_lint` to construct a bidirectional title lookup table that maps both file stems and YAML `title` attributes, eliminating over 200 false positives.

### 14. API Rate Limit Flooding from High Concurrency
- **Problem:** Concurrently extracting chunks and auditing pages with 5+ parallel workers immediately triggered provider rate limits and HTTP 429 errors.
- **Resolution:** Reduced worker semaphores to 2 concurrent tasks and introduced 0.3s to 1.5s pacing sleeps between chunk requests.

### 15. Ingestion of Incomplete Files During Background Sync
- **Problem:** In background watcher mode, files being synchronized over the network via Syncthing or written slowly by external editors were detected immediately, causing the engine to ingest half-written, corrupted files.
- **Resolution:** Implemented a multi-iteration stability loop in `watch_cmd.py` that polls file size and modification timestamps across 15 iterations (with 1-second sleeps), verifying that file writes have completely stabilized before triggering compilation.

### 16. Event Loop Collisions in Asynchronous Execution
- **Problem:** Calling `asyncio.run()` inside functions called by existing asynchronous event loops (such as FastAPI or Starlette) threw `RuntimeError: asyncio.run() cannot be called from a running event loop`.
- **Resolution:** Standardized core functions on native `async/await` patterns, reserving `asyncio.run()` exclusively for top-level synchronous CLI dispatchers.

### 17. Truncated Synthesis Output Written to Disk
- **Problem:** Occasional LLM completion cutoffs produced tiny markdown stubs (less than 50 characters) or files lacking YAML frontmatter, corrupting vault structure.
- **Resolution:** Added a strict completeness filter in `lib/wiki_ops.py` that validates that synthesized pages are at least 100 characters long and contain both a valid `title` and `type` attribute in their frontmatter before staging them for human review.

### 18. Vault Directory Name Resolution Inflexibility
- **Problem:** Running CLI commands with short vault names (e.g., `wiki status -w ai`) failed because the system expected exact directory names (e.g., `ai-chats-wiki`).
- **Resolution:** Enhanced `resolve_vault_path` in `lib/utils.py` to match short names, strip `-wiki` suffixes, and semantically infer the target vault from query text when multiple vaults exist.

## 10. Future Architectural Trajectory & Next-Gen Roadmap

The following advanced capabilities represent the active roadmap for future iterations of LLM Wiki:
1. **Asymmetric Model Routing:** Routing the extraction phase to ultra-fast, inexpensive models (e.g., Gemini 1.5 Flash or local Ollama models) while reserving high-end frontier models exclusively for synthesis, reducing operational costs by over 80%.
2. **Multimodal Vision Ingestion:** Integrating local and cloud vision models to ingest diagrams, tables, charts, and technical schematics from PDFs and image files directly into structured Markdown tables.
3. **Automated Confidence Decay:** Implementing background timestamp monitors that systematically decay note confidence ratings over time if external sources or periodic audits do not actively corroborate their claims.
4. **Interactive Graph UI:** Expanding the FastAPI dashboard to render interactive 3D force-directed knowledge graphs visualizing note connections, cluster density, and authority hubs directly in the browser.
